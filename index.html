Swing-Trading Signal System

An Android app that scores Indian equities BUY / HOLD / SELL from live market data, backed by a Spring Boot service that supplies the news-sentiment layer.

  • Kotlin
  • Compose
  • Spring Boot
  • PostgreSQL
Read more Show less

Swing trades are held for days to weeks, so the decision rests on price action, order-book pressure and the news all at once. I wanted one number I could argue with rather than a black box — so the app shows the verdict and every input underneath it.

How the signal works

Three layers combine into a score from −100 to +100, which maps to a verdict and a confidence value.

  • 45% Technicals — RSI against its midpoint, price against SMA-50, and SMA-20 against SMA-50, each scaled and clamped, computed from live candles.
  • 35% Sentiment — FinBERT over Indian financial news.
  • 20% Order-book depth — buy/sell pressure, which can veto a signal outright even when the weighted score is strong.

Android app

Kotlin and Jetpack Compose, MVVM with StateFlow and unidirectional data flow. Live quotes and the full order book on a 20-second poll, a WebSocket price stream sampled to 1 s, charts drawn on Compose Canvas, and an on-disk candle cache so a cold start doesn't refetch history for fifty stocks. Dependency injection is done by hand — one container picks the implementations — because Hilt was more machinery than a single-user app needed.

Sentiment backend

Spring Boot and Java with a small Python FastAPI service for the model, Postgres behind Flyway, the whole thing shipped as Docker Compose. It polls six Indian financial-news RSS feeds, matches each headline against roughly 2,700 NSE instruments, scores it with FinBERT and stores it permanently with its timestamp. Windows from 30 minutes to a month are re-aggregations of those stored scores, computed on demand rather than precomputed.

Decisions I'd defend

  • News and crowd sentiment are never blended. They are two readings, always. When they disagree, that disagreement is itself information.
  • Every percentage travels with its item count, and below five items the reading is withheld entirely — "70% of 2 articles" is noise dressed as a number.
  • Baselines are per stock. A stock that always reads 60% bullish is not bullish news, so each reading carries its own historical normal and how many standard deviations it sits from it.
  • The model stayed in Python. Running FinBERT from Java meant an ONNX export and a hand-ported tokenizer; one HTTP endpoint was the cheaper boundary.
  • Failures surface instead of degrading quietly. A chart that can't load shows an error — a sample chart next to a live price is worse than no chart.

Where it stands

Technicals, depth, charts and the live price stream all run on real broker data. The sentiment service is mid-build; until it is hosted somewhere the phone can reach, the app labels that layer as sample data in the UI rather than quietly faking it.

Kharcha — Expense Manager

An offline-first Android app for tracking day-to-day spending against a monthly budget. No backend, no accounts, no network.

  • Kotlin
  • Compose
  • Room
Read more Show less

A personal expense manager for everyday rupee spending: log what you spent, see how you're pacing against the month's budget, and find out where the money actually went.

The constraint that shaped it

Entirely offline, with no backend at all — no servers, no sync, no accounts, no third-party APIs. Everything lives on the device. That keeps running cost at zero, and it means the privacy question answers itself: spending data never leaves the phone, so there is nothing to breach.

How it's built

Kotlin with Jetpack Compose and Material 3, structured as MVVM — composable screens to ViewModel to repository to Room. Room is the single source of truth and everything is exposed as Flow, so a new transaction redraws the budget bar, the history list and the charts without any of them asking. Five screens: home with budget pacing, add-transaction, history grouped by day, insights with category breakdowns, settings.

Why it matters to me

It is my first Android app, and I came to it from a C++ and competitive-programming background — so Compose's state model, the Activity lifecycle and Room were all new ground. It is also the app that has to clear a new Play Console account's closed-testing requirement, which meant it had to be genuinely useful rather than a throwaway.

Where it stands

Built and in testing ahead of a Play Store release. The privacy policy is already published.

At Walmart

Document Intake Agent

An event-driven service that replaces manual triage of incoming legal documents with a four-stage LLM agent pipeline.

  • Python
  • Kafka
  • Kubernetes
Read more Show less

Legal documents served against the company used to be triaged by hand: someone read the PDF, worked out what kind of matter it was, decided which attorney and paralegal should own it, and opened the case. This service does that intake automatically.

The pipeline

A Kafka consumer picks up document events, pulls the PDF, and runs it through four LLM-backed stages that share session state — extract → classify → summarise → assign — then files the result into the downstream case-management system over REST, with the owners already attached.

Why Kafka rather than a webhook

At-least-once delivery with replay. If the pipeline or anything downstream is unavailable, the offset simply isn't committed and the message comes back on the next poll. Nothing is dropped, and the upstream system doesn't have to grow retry logic of its own to make that true.

Around the pipeline

  • A FastAPI service for manual re-runs and health checks
  • Prometheus metrics and a SQL audit trail for every decision the agent makes
  • A vector database for similar-matter search, with embeddings backfilled across historical records
  • A regression harness, so prompt and model changes are measured rather than guessed at

Also at Walmart

Backend services in Java and Spring Boot, with Redis and Guava caching on the read paths, containerised with Docker and run on Kubernetes.
